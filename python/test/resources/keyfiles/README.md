# Sample key files

> **Why these are not in `app/src/test/resources/`**, where the export fixtures live: those are
> *bundles* — the zip contents the Android importer reads, which is why both sides' tests share
> them. These are exporter **inputs**, consumed before a bundle exists. Java never sees a `.keys`
> file and has no reason to.

Self-generated tags — OpenHaystack and friends — in every format the exporter reads. Drop one on
the wizard's **+ Add from key file…** button, or pass it to the CLI:

```shell
uv run python -m exporter.cli --no-password --add-keys test/resources/keyfiles/Wallet.keys
```

| File | Format |
| --- | --- |
| `macless-haystack-devices.json` | Macless Haystack's `devices.json` — base64 `privateKey` plus `additionalKeys` |
| `findmy-custom-accessory.json` | FindMy.py's own `custom_rolling_key_accessory` JSON — hex keys |
| `Wallet.keys` | An OpenHaystack `.keys` file — `Private key:` / `Advertisement key:` lines |
| `bare-keys.txt` | Whatever people actually have: one key per line, `#` comments allowed |
| `Swapped.keys` | **Deliberately broken** — see below |

## Four different tags

One per format, and deliberately not the same tag four times. They were, at first — and the
exporter refused the second one as a duplicate, which was correct: an identifier is derived from a
tag's own public key, so the same keys are the same tag however the file spelled them. A sample set
that cannot be imported together is a poor sample set, so these are four distinct tags.

Importing the same file twice still refuses, which is worth trying.

## Nothing here is a real tag

The private keys are fixed byte patterns, generated by a loop. No tag has ever advertised them, so
nothing in this directory can locate anything.

They are still *valid* keys — 28 bytes on SECP224R1, which is what a Find My accessory uses — so
they exercise the real code paths rather than a shortcut for tests.

## `Swapped.keys` is meant to fail

It has the advertisement key in the `Private key:` field: the likeliest real mistake somebody makes
with these files, and one **nothing can see by looking**, because a private key and a public one
are both 28 bytes.

Importing it is refused, because `Wallet.keys` states an advertisement key and the exporter checks
that the private key actually derives it. Without that check the export succeeds and produces a tag
that never appears on the map, with nothing anywhere to explain why.

## Keeping them honest

`test/test_keyfile_fixtures.py` parses every one of these. A sample that stopped working would
otherwise be discovered by whoever was trying the feature out for the first time.
